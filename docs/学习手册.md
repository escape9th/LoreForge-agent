# LoreForge 第一版学习手册

这份文档把你当成第一次接触 Agent 的人，从“它到底解决什么问题”开始讲。

## 1. 它解决什么问题

假设你想做一个游戏，主题是“海洋灾变后的漂浮城市”。

你通常需要先查资料：

- 能源怎么来？
- 漂浮结构怎么维护？
- 资源不够时，社区怎么分配？

普通 AI 可以直接写一篇很长的设定，但你不知道它哪些内容来自资料，哪些内容是它自己编的。

LoreForge 的做法是把两件事分开：

1. **事实**：必须尽量能在证据中找到支持。
2. **创作提案**：可以大胆原创，但要明确标成提案。

这就是“证据驱动创作”。

## 2. 运行一次会发生什么

运行：

```powershell
python -m loreforge run "设计一个受海洋灾变影响的漂浮城市游戏世界观" --out demo-output
```

程序依次走五步：

```text
需求
 ↓
plan      拆研究问题
 ↓
gather    找资料
 ↓
extract   保存证据
 ↓
draft     生成创作蓝图
 ↓
verify    检查事实是否有证据
```

## 3. 为什么这叫 Agent

Agent 不只是“调用一次模型”。

一个更有工程含义的 Agent，至少需要：

- 目标：用户的创作需求；
- 计划：下一步要研究什么；
- 工具：搜索和读取资料；
- 状态：记住已经找到什么；
- 判断：决定输出是否有证据；
- 结果：给出可行动的方案。

本 Demo 把这些步骤写成代码，所以你能看见每一步，而不是把所有事情放进一个巨大提示词。

## 4. 先看数据模型

打开 `src/loreforge/domain.py`。

`ResearchBrief` 表示用户输入的需求。它有两个字段：

- `prompt`：需求文字；
- `run_id`：这次运行的唯一编号。

`Source` 表示一个来源：

- `source_id`：内部编号；
- `title`：标题；
- `url`：地址；
- `text`：可以被引用的资料内容。

`Evidence` 表示从来源中拿出来的证据。它只保存来源编号和证据原文，这样报告可以追溯回来源。

`Claim` 表示一句声明。它有 `kind`：

- `fact`：资料事实；
- `proposal`：原创提案。

这个小字段非常重要。没有它，事实和幻想会混在一起。

## 5. 再看 Demo Provider

打开 `src/loreforge/demo.py`。

`DemoSearchProvider` 是一个假的搜索服务，但它遵循真实搜索服务应该有的接口：

```python
search(query, limit) -> list[Source]
```

它从内置资料目录中找相关内容。以后换成真实搜索 API，只需要换这个 Provider，工作流不用重写。

`DemoModelProvider` 也遵循接口：

```python
plan(brief) -> list[ResearchQuestion]
draft(brief, questions, sources) -> CreativeBlueprint
```

第一版故意使用确定性结果。这样没有 API Key 时，面试官也能运行项目，每次结果也一致。

## 6. 工作流到底做了什么

打开 `src/loreforge/workflow.py`。

`run_research()` 是主入口。

第一步创建 `ResearchBrief`。空字符串会立刻报错，因为没有研究需求就没有 Agent 任务。

第二步调用 `model.plan()`，生成三个研究问题。

第三步对每个问题调用 `search.search()`，把结果放进列表。然后用规范化 URL 做字典键，自动删除重复来源。

第四步把每个来源的正文保存为 `Evidence`。真实版本可以在这里做网页正文抽取、段落切分和引用定位。

第五步调用 `model.draft()`。返回值里明确有：

- `facts`
- `proposals`
- `sections`

第六步只核验 `facts`。原创提案不需要假装拥有外部证据。

## 7. 核验器如何工作

打开 `src/loreforge/verification.py`。

第一版使用简单、透明的关键词重叠：

1. 把声明和证据切成中文双字词、英文词和数字；
2. 计算声明词语有多少出现在证据里；
3. 超过一半就标成 `supported`；
4. 否则标成 `unverified`。

这不是完美的事实核查器，但它有三个优点：

- 代码短；
- 行为可解释；
- 测试容易写。

以后可以替换成 NLI 模型、向量检索或 LLM Judge，但仍然应该保留 `supported/unverified` 这种清晰结果。

## 8. 报告为什么同时有 Markdown 和 JSON

Markdown 给人读，JSON 给程序读。

Markdown 适合直接放进作品集、Issue 或创作笔记。

JSON 适合：

- 后续做 Web 页面；
- 保存运行历史；
- 重新计算评测；
- 记录 Agent 轨迹；
- 接入数据库。

这也是一个很常见的工程思路：展示层和数据层分开。

## 9. 测试怎么看

运行：

```powershell
python -m pytest -q
```

测试分三类：

- `test_domain.py`：数据模型是否拒绝错误输入；
- `test_verification.py`：有证据和没证据时是否判断正确；
- `test_workflow.py`：整条 Agent 流程是否完整；
- `test_cli.py`：命令行是否真的生成报告；
- `test_evaluation.py`：Demo 是否达到最低质量线。

面试时可以这样解释：

> 我没有只测试最后一段文本，而是测试 Agent 的状态流、工具边界、核验结果和可交付文件。

## 10. 从零复现

1. 安装 Python 3.11 或更高版本。
2. 进入项目根目录。
3. 运行 `python -m pytest -q`。
4. 运行 Demo 命令。
5. 打开输出目录中的 Markdown。
6. 打开 JSON，观察 `sources`、`evidence`、`blueprint`、`verification` 和 `trace`。
7. 修改 `demo.py` 中的一条事实。
8. 再运行测试，观察核验结果如何变化。

## 11. 你应该记住的底层思想

最重要的不是“用了多少 Agent 框架”，而是下面这句话：

> 让模型负责生成和判断候选内容，让代码负责状态、边界、追踪和最终约束。

模型擅长语言和联想。代码擅长限制、重复执行和验证。LoreForge 把两者放在各自擅长的位置。
