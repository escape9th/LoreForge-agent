# LoreForge 项目完全解读与面试手册

这份文档的目标不是让你背术语，而是让你能从代码、运行过程和工程取舍三个角度解释 LoreForge。读完后，你应该能回答“它为什么有用”“一次请求怎么跑”“RAG 和 Tool Calling 到底在哪里”“为什么不用某个框架”以及“生产环境怎么扩展”。

## 1. 一句话介绍

LoreForge 是一个面向游戏、动漫和小说创作的证据驱动研究 Agent：它把用户需求拆成问题，让模型选择检索工具，保存来源和证据，生成事实与原创提案分离的创作蓝图，再检查事实是否有证据支持。

面试版说法：

> 我做了一个可离线复现、也能接入 OpenAI-compatible 模型的创作研究 Agent。它包含 RAG、Tool Calling、结构化输出、引用核验、执行轨迹、FastAPI、SQLite 和自动评测。重点不是套框架，而是把模型决策和确定性工程边界分开。

## 2. 它解决什么问题

普通聊天模型可以快速生成世界观，但有三个问题：

1. 资料事实和模型原创混在一起。
2. 不知道回答引用了哪些来源。
3. 模型做过什么决策无法复盘。

LoreForge 把输出拆成 `facts` 和 `proposals`。事实进入引用核验，原创提案明确标记为 proposal。检索和来源读取通过工具完成，每次调用进入 `tool_trace`。

## 3. 先理解六个核心概念

### Agent

Agent 不是“调用一次大模型”。这里的 Agent 包含目标、状态、工具、循环、停止条件和结果。模型负责选择动作，普通代码负责允许哪些动作、怎样执行、最多执行几次以及怎样记录。

### RAG

RAG 是 Retrieval-Augmented Generation，中文叫检索增强生成。先检索外部资料，再把资料交给模型生成，降低只靠模型参数记忆回答的风险。

LoreForge 的链路是：

```text
用户需求 -> 词项召回 -> Source -> Evidence -> 生成 -> 引用核验
```

当前召回算法较轻，目的是离线、透明、易测。`SearchProvider` 是替换边界，生产版可以接向量数据库、BM25、reranker 或搜索 API。

### Tool Calling

Tool Calling 不是模型直接执行函数。模型只返回“我想调用哪个工具以及参数是什么”。应用程序解析和校验后，才执行注册过的工具，再把结果发回模型。

```json
{
  "type": "tool_call",
  "name": "corpus_search",
  "arguments": {"query": "漂浮城市能源", "limit": 3}
}
```

模型不能随意执行 Python，也不能调用未注册工具。这是安全边界。

### Structured Output

结构化输出就是要求模型返回固定 JSON 结构，而不是任意文字。程序可以验证字段并继续处理。LoreForge 的规划、创作蓝图和工具动作都是结构化对象。

### Trace / Observability

Trace 是执行轨迹。普通 `trace` 记录 plan、gather、extract、draft、verify 五个阶段；`tool_trace` 记录工具名、输入、结果、成功或失败、时间戳。它用于调试、评测、审计和面试演示。

### Evaluation

单元测试检查代码行为，评测检查 Agent 输出是否达到质量线。LoreForge 的评测包括：研究问题、来源、证据、事实与提案分离、核验结果、工具轨迹、工具成功状态。

## 4. 一次请求的完整链路

假设运行：

```powershell
python scripts\run_demo.py run "设计一个资源冲突的游戏任务线" --out demo-output
```

完整过程如下：

1. `cli.py` 解析命令和参数。
2. `Settings.from_env()` 判断使用离线 Provider 还是真实模型。
3. `run_research()` 创建 `ResearchBrief` 和唯一 `run_id`。
4. `ModelProvider.plan()` 生成研究问题。
5. `ToolCallingAgent` 请求下一步动作。
6. Demo 或真实模型选择 `corpus_search`。
7. `ToolRegistry` 查找工具，校验 `query`，执行 `SearchProvider.search()`。
8. 工具返回 JSON 数据，Agent 保存 `ToolTraceEvent`。
9. Agent 可继续调用 `source_lookup`，也可以结束。
10. 工作流对 Source 去重并生成 Evidence。
11. `ModelProvider.draft()` 生成 `CreativeBlueprint`。
12. `verify_claims()` 只核验事实，不核验原创提案。
13. `ResearchPackage` 聚合问题、来源、证据、蓝图、核验和两类轨迹。
14. 报告写成 Markdown 和 JSON；带 `--db` 时保存完整 JSON 快照到 SQLite。

API 调用与 CLI 的区别只在入口：`POST /runs` 进入 `RunService`，后面复用同一条工作流。

## 5. 文件阅读顺序

建议按下面顺序读，不要从 API 文件开始乱跳：

1. `src/loreforge/domain.py`：认识系统里有哪些数据。
2. `src/loreforge/tools.py`：理解工具 schema、注册和执行边界。
3. `src/loreforge/toolcalling.py`：看模型与工具如何循环。
4. `src/loreforge/demo.py`：看离线模型如何确定性地规划和选工具。
5. `src/loreforge/adapters.py`：看真实模型协议和自定义资料库。
6. `src/loreforge/workflow.py`：把全部组件串起来。
7. `src/loreforge/verification.py`：看事实核验。
8. `src/loreforge/service.py`、`repository.py`：看服务复用和持久化。
9. `src/loreforge/api.py`、`cli.py`：看两个入口。
10. `tests/` 和 `evaluation/`：看系统承诺了哪些行为。

## 6. 核心模块逐个解释

### domain.py

这里没有网络和数据库，只定义业务数据。`ResearchPackage` 是一次运行的最终快照。使用 dataclass 的原因是结构简单、可比较、可序列化、标准库足够。

`from_dict()` 很重要：SQLite 保存 JSON，读取时必须恢复成领域对象。它对旧版没有 `tool_trace` 的快照使用空列表，因此 v0.3 数据仍可读取。

### tools.py

`ToolSpec` 描述给模型看的工具：名称、说明、参数 JSON Schema。

`Tool` 包装真正的 Python handler，并检查必填参数。异常不会让整个 Agent 崩溃，而是变成 `ToolResult(ok=False)`。

`ToolRegistry` 是白名单。模型给出名字后，只有注册表中的工具可以执行。

四个内置工具：

- `corpus_search`：按查询检索来源。
- `source_lookup`：按 source_id 读取完整来源。
- `citation_check`：检查声明与证据的词项重叠。
- `consistency_check`：检查文本是否满足给定约束。

### toolcalling.py

`ToolCallingAgent.run()` 是循环核心。每轮：请求模型动作、判断动作类型、执行工具、记录结果、收集来源。`max_tool_calls` 保证模型即使不断要求调用也会停止。

为什么循环放在独立文件？因为工具选择策略、工具执行和外层创作流程是不同职责，可以分别测试和替换。

### demo.py

Demo Provider 不是伪装成智能模型，而是一个确定性的协议替身。它先调用 `corpus_search`，再读取第一个来源，最后返回 final。价值是：没有密钥、没有网络、CI 中也能完整演示 Tool Calling。

### adapters.py

`OpenAICompatibleModelProvider` 处理普通结构化生成；`OpenAICompatibleToolCallingProvider` 处理工具动作。

真实 Tool Calling 的关键协议：

1. 请求包含 `tools` JSON Schema 和 `tool_choice: auto`。
2. 模型返回 assistant 消息里的 `tool_calls`。
3. 应用执行工具。
4. 下一轮请求必须重放 assistant 的 `tool_calls`。
5. 工具结果使用 `role=tool`，并带相同 `tool_call_id`。

漏掉第 4 或第 5 步，严格的兼容服务会拒绝请求。

### workflow.py

工作流是确定性的总控层。模型能决定调用哪个工具，但不能改变“先规划、后收集、再生成和核验”的业务约束。这样既有 Agent 灵活性，也保持可测试性。

### verification.py

核验器把中英文文本转换成词项，计算重叠比例。它不是严格事实核查，但透明、稳定、可离线。生产升级可以换成混合检索加 NLI 或 LLM Judge，同时保留当前结构化报告接口。

### repository.py 和 service.py

Repository 只管 SQLite。Service 负责选择 Provider、运行工作流、保存和读取。CLI 和 API 都调用 Service，避免两套业务逻辑。

## 7. 为什么没有使用 LangChain

标准回答：

> 这个版本的目标是展示底层机制，所以我用小型协议和标准库实现。这样 Tool Calling 消息、工具白名单、状态和停止条件都能直接看见，也避免为了四个工具引入较大依赖。生产项目如果需要大量连接器、复杂图工作流或团队已有 LangChain/LangGraph 基础，我会评估接入，但领域对象、工具接口和评测仍然可以保留。

不要回答“LangChain 不好”。技术选择取决于场景。

## 8. 为什么没有向量数据库

标准回答：

> 当前语料小，关键词召回更透明、部署成本低，足够验证 Agent 架构。项目已经通过 SearchProvider 隔离检索实现。语料扩大后，我会采用混合检索：BM25 保留关键词精确匹配，embedding 提供语义召回，reranker 重排，再用离线评测比较 Recall@K、MRR 和回答引用正确率，而不是为了关键词堆技术。

## 9. 失败和安全怎么处理

- 空 prompt 在领域入口拒绝。
- 未注册工具返回结构化错误，不执行任意代码。
- 缺少必填参数返回错误轨迹。
- 工具异常被捕获并记录。
- 无效模型 JSON 抛出清晰 ValueError。
- 调用次数有上限，防止死循环和费用失控。
- API Key 只进入 Authorization header，不进入 trace。
- 事实必须经过核验；没有支持则标记 `unverified`。

生产环境仍需补：认证、租户隔离、速率限制、工具级权限、敏感信息脱敏、网络出口白名单、超时重试、费用和 token 统计。

## 10. 测试策略

测试分层：

- 领域测试：输入和序列化。
- 工具测试：schema、参数、成功与失败结果。
- Agent 测试：循环、未知工具、调用上限。
- Adapter 测试：真实协议 payload 和解析，不访问网络。
- 工作流测试：端到端领域结果和轨迹。
- Repository/Service/API/CLI 测试：外层入口和持久化。
- Evaluation：作品质量线。

面试时强调：模型具有随机性，但协议、状态转换、安全边界和评测可以确定性测试。

## 13. 常见面试问题与参考回答

### 这个项目最难的部分是什么？

不是调用模型，而是定义稳定边界：模型输出会变化，但工具白名单、参数校验、调用上限、状态结构和引用核验必须确定。真实模型协议还要求正确重放 tool_calls 和 tool_call_id。

### Tool Calling 和普通函数调用有什么区别？

普通函数调用由程序员写死。Tool Calling 是模型根据上下文提出函数名和参数，但最终执行权仍在应用程序。

### 这算多 Agent 吗？

不算。当前是一个 Agent 在有界循环中使用多个工具。多 Agent 需要多个独立角色、状态或策略之间的协调。项目可以扩展，但不应该把工具当 Agent 来宣传。

### 如何避免幻觉？

不能完全避免。这里通过外部证据、事实与提案分离、引用核验、结构化状态和 unverified 标签降低风险。生产版还需要更好的检索、引用定位和人工审核。

### SQLite 为什么保存 JSON 快照？

当前主要需求是复盘整次运行，而不是复杂统计。JSON 快照开发快、恢复领域对象简单，摘要列支持列表查询。规模变大后再拆 tool_calls、sources、metrics 等表。

### 如何扩展成多 Agent？

可以增加 Planner、Researcher、Writer、Verifier 四个角色，共享类型化状态，由 supervisor 控制转换。但先要有路由正确率、成本和延迟评测，否则只是把一次调用拆成更多调用。

### 如何做生产级 RAG？

增加文档解析、分块、embedding、混合召回、reranker、元数据过滤、引用段落定位和离线检索评测。重点指标包括 Recall@K、MRR、faithfulness、citation precision、延迟和成本。

### 如何观察线上问题？

在现有 trace 上增加 trace_id、模型名、token、费用、阶段耗时、重试次数、错误类型和脱敏后的输入输出，再接 OpenTelemetry 和监控平台。

## 14. 你必须诚实说出的限制

- 内置语料是演示资料，不是实时互联网。
- 当前检索不是 embedding 向量检索。
- 核验是词项重叠，不是完整事实证明。
- consistency_check 是轻量约束检查。
- 没有认证、队列、租户和前端。
- 真实兼容模型的具体差异需要按服务商验证。

诚实说明限制不会降低项目含金量。能解释边界和升级路线，反而说明你理解工程。

## 15. 最后记住这四句话

1. 模型负责提出动作，程序负责控制执行。
2. RAG 的核心不是向量数据库，而是让生成建立在可追溯的外部证据上。
3. Agent 的价值不只是会调用工具，还要有状态、边界、停止条件和可观测性。
4. 一个能离线复现、能测试、能解释失败的项目，比堆很多框架名更可信。
